# AdaVoice — План готовності до продакшну

**Питання, на яке це відповідає:** *що має бути правдою, перш ніж оператор покладеться на цей застосунок для свого
реального робочого дня?*

Це **перешкода релізу** — визначення "готово до продакшну". Воно перетинає
фази в [плані реалізації](implementation-plan.md); багато пунктів *будуються* у
Phases 1–5, але *підписуються* лише тут, проти реального обладнання і реального дзвінка. Джерела: NFR в
[design 01 §7](../design/01-overview.md#7-non-functional-requirements), граничні випадки і ризики в
[design 07](../design/07-risks-security.md) і стратегія тестування в
[design 08](../design/08-testing.md).

> **Статус:** не розпочато. Ця перешкода — фінальний крок Phase 5; чек-лист ручного дзвінка
> всередині неї також виконується раніше (Phase 0 і пілот після Phase 3) як суха репетиція.

---

## Визначення готовності до продакшну

> AdaVoice готовий до продакшну, коли оператор може завершити **повний реальний робочий день на ньому
> без допомоги розробника**, живий мікрофон **ніколи тихо не зупиняється**, а її голосові дані
> **відновлювані** навіть після збою чи пошкодженого файлу.

Перешкода виконана лише тоді, коли **кожен бокс нижче позначено на цільовій машині**, а не в теорії.

## 1. Надійність і відновлення (критична для засобу до існування частина)

- [ ] Наскрізна передача мікрофона (passthrough) ніколи *тихо* не зупиняється — будь-який збій піднімає стан **DEGRADED**, який
      гучно видимий **і** чутний на **системному пристрої за замовчуванням** (не на опціональному monitor).
- [ ] Від'єднання/під'єднання пристрою під час дзвінка авто-відновлюється (watchdog + перебудова з backoff).
- [ ] Збій застосунку → Windows перезапускає його (`RegisterApplicationRestart`); рушій авто-відновлюється;
      показано toast "recovered"; нечистий вихід залоговано через heartbeat.
- [ ] 8-годинний soak проходить: події дрейфу залоговано < кількох/годину; RSS рівний (без витоку).
- [ ] Зависання запиту render > 500 ms запускає рівно одну перебудову.
- [ ] Запуск другого екземпляра фокусує перше вікно (single-instance mutex).

## 2. Якість аудіо і затримка — latency (перевірено на обладнанні, не спроєктовано)

Виконати [чек-лист ручного тесту дзвінка, design 08 §4](../design/08-testing.md) проти реального дзвінка
Zoho. Підмножина-перешкода:

- [ ] Дальній кінець чує фрази чітко — розбірливість не зачеплена Chrome NS/EC/**AGC** (A6).
- [ ] Живий голос між фразами чистий; немає стрибка рівня на межах фраз.
- [ ] Приглушений (ducked) мікрофон справді звучить приглушеним для дальнього кінця, після AGC.
- [ ] Тригер→cable < 100 ms; **затримку (latency) mouth-to-Chrome виміряно і записано** (A11).
- [ ] Відмова від комунікаційного приглушення (ducking) тримається через повторні цикли старт/стоп дзвінка.
- [ ] Запасний варіант під час дзвінка відрепетировано: переключити мікрофон Chrome на апаратну гарнітуру без перепідключення.

## 3. Покриття тестами і CI

- [ ] Unit-набори зелені: машина станів (кожен перехід), mixer, рампи приглушення (ducking),
      одне відтворення, OFF AIR, watchdog, політика дрейфу.
- [ ] Golden-file DSP набір зелений: trim, узгодження гучності (RMS ±0.5 dB, пік ≤ −3 dBFS), fade.
- [ ] Storage-набір зелений: симуляція kill-9 атомарного запису, відновлення після пошкодження, orphan,
      round-trip export→import.
- [ ] Services-набір зелений: показ конфлікту hotkey, **повнота локалізації (uk/pl/en)**.
- [ ] CI ганяє unit + golden-file набори на кожному коміті і зелений на коміті релізу.

## 4. Безпека даних

- [ ] Щоденний резервний zip включає `library.json`, `settings.json`, **і `audio/`**; тримає 7.
- [ ] Відновлення перевірено: імпорт резервного zip на чистій машині відтворює бібліотеку без втрат.
- [ ] Пошкоджений `library.json` відновлюється з найновішої копії під час старту — ніколи не стартує тихо порожнім.
- [ ] Видалення зберігає WAV як `deleted-{id}.wav` (голосові записи ніколи не невідновлювані).
- [ ] Повний диск посеред запису чисто перериває дубль; тимчасовий файл видалено; бібліотека недоторкана.

## 5. Спостережуваність

- [ ] Serilog rolling-file логування на місці; збої аудіо, події дрейфу і зміни станів
      діагностовні постфактум.
- [ ] Тривоги стану рушія підключено (DEGRADED чутна незалежно від налаштування monitor).
- [ ] Розташування логів задокументовано в посібнику користувача для підтримки.

## 6. Безпека і приватність

- [ ] Нуль мережевих викликів (offline перевірено — без телеметрії, без акаунтів).
- [ ] Записи і метадані лишаються під `%LOCALAPPDATA%\AdaVoice\`.
- [ ] Резервні копії/експорти — це незашифровані zip — **задокументовано для користувача** (шифрування — після MVP).
- [ ] Застосунок ніколи не захоплює бік клієнта в розмові.
- [ ] Попередження SmartScreen про непідписаний інсталятор **задокументовано зі скриншотом** (рішення #19).

## 7. Встановлення і розповсюдження

- [ ] Інсталятор Inno Setup, **self-contained .NET 10** успішно проходить на **чистій Windows VM** без
      завантаження runtime.
- [ ] Setup wizard проходить усі перевірки середовища на чистій машині: detect/verify VB-CABLE,
      приватність мікрофона, cable = 48 kHz, вихід за замовчуванням ≠ CABLE Input, сесію не заглушено,
      Communications = "Do nothing".
- [ ] Loopback-самотест і картка впевненості першого дзвінка (рішення #24) працюють end-to-end.
- [ ] Встановлення VB-CABLE кероване майстром (не можна бандлити — ліцензування).

## 8. Документація і підтримка

- [ ] Посібник користувача: налаштування, **збірник запасних дій** ([design 07 §5](../design/07-risks-security.md)),
      скриншоти вибору мікрофона Zoho, нота SmartScreen, де живуть логи.
- [ ] [handoff.md](../../handoff.md) відображає фінальний стан.

## 9. Прийняття (єдиний користувач)

- [ ] Знахідки контрольованого пілоту після Phase 3 опрацьовано (розміри кнопок, значення duck за замовчуванням, робочий процес
      категорій, ергономіка Topmost, ясність OFF AIR).
- [ ] **Фінальне прийняття:** оператор завершує повний реальний робочий день на AdaVoice без
      допомоги розробника (вихід Phase 5, [roadmap](../roadmaps/mvp-roadmap.md)).

## Підпис

Реліз v1 лише коли секції 1–9 повністю позначено **на цільовій машині**. Будь-який непозначений
критичний для засобу до існування пункт (§1) чи апаратний аудіо-пункт (§2) — це жорсткий блокер, а не відома проблема.
