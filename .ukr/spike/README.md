# Spike для Phase 0 — Architecture A (VB-CABLE + внутрішній мікшер застосунку)

**Одноразовий консольний прототип** згідно з [MVP roadmap](../docs/roadmaps/mvp-roadmap.md).
Це не production-код; нічого звідси не випускається. Єдиний повторно використовуваний артефакт —
це `DuckingOptOut.cs` — COM-прокладка `IAudioSessionControl2::SetDuckingPreference`,
яку NAudio не обгортає (еталонна реалізація для Phase 1).

## Ворота дозволу — вирішено

**A8 — угоди з роботодавцем/Zoho не потрібно (роботодавець лояльний), підтверджено 2026-06-13.**
Більше не ворота (design 01 §4, рішення #20). Цей spike усе ще має дати відповідь на
*технічні* невідомі A5/A6 — чи пропускає Zoho/Chrome попередньо записане мовлення через AGC
розбірливо — див. тестову матрицю нижче.

## Передумови (цільова машина)

1. **VB-CABLE** — https://vb-audio.com/Cable/ (donationware; встановлюйте вручну,
   ніколи не поширюйте). Перезавантажте систему після встановлення.
2. Налаштування звуку: встановіть **обидва** — "CABLE Input" (відтворення) і "CABLE Output"
   (запис) — на **48000 Hz** (Properties → Advanced).
3. Sound → Communications → **"Do nothing"** (про всяк випадок, для ducking).
4. Вивід за замовчуванням НЕ має бути CABLE Input (інакше ви нічого не почуєте).
5. .NET 10 SDK (вже на цій машині: 10.0.202).

## Запуск

```powershell
cd C:\p\ada-voice\spike\AdaVoice.Spike
dotnet run -- --list                  # enumerate devices
dotnet run                            # default comms mic -> CABLE Input
dotnet run -- --mic "USB Audio"       # pick mic by name substring
dotnet run -- --phrases C:\path\wavs  # real recorded phrases (recommended)
```

З WSL: `"/mnt/c/Program Files/dotnet/dotnet.exe" run` у каталозі проєкту
(аудіо все одно працює на боці Windows).

Клавіші: `1-9` відтворити фразу · `S` зупинити (затухання 10 ms) · `D` ducking увімк/вимк ·
`+/-` ducking dB · `L` самотест latency trigger→cable · `I` статистика буфера · `Q` вихід.

Без `--phrases` генеруються три синтетичні WAV (тон, sweep у мовній смузі,
AM-сплески). **Справжній тест AGC потребує записаних людських фраз** — запишіть
кілька речень в Audacity (48 kHz моно WAV) і передайте папку.

## Тестова матриця Phase 0 (критерії виходу з roadmap)

- [x] **A8**: дозвіл роботодавця/Zoho — вирішено 2026-06-13 (угода не потрібна; роботодавець лояльний)
- [ ] Chrome бачить "CABLE Output" як мікрофон; дзвінок Zoho з ним з'єднується
- [ ] Passthrough: дальня сторона чітко чує живий голос через spike
- [ ] Фрази розбірливі для дальньої сторони **після AGC (post-AGC)** (використовуйте записане мовлення, а не тестові тони)
- [ ] Ducking чутно працює на дальній стороні; перевірте, чи AGC у Chrome знову підсилює приглушений мікрофон
- [ ] Самотест `L`: trigger→cable **< 100 ms** (підлаштуйте latency у панелі керування VB-CABLE, якщо більше)
- [ ] **Наскрізно від рота до Chrome**: запишіть те, що отримує Chrome (наприклад, друга
      машина в дзвінку або дампи chrome://webrtc-internals), плескаючи в долоні; виміряйте зсув
- [ ] Відмова від ducking **тримається упродовж циклів старту/стопу дзвінка** (запустіть/зупиніть кілька дзвінків Zoho;
      рівень фрази/passthrough не має просідати, коли дзвінок починається)
- [ ] Passthrough стабільний протягом **1 h** (стежте за `I` щодо ритму overrun; логуйте кількості)
- [ ] Матриця AGC: перевірте Zoho/Chrome на перемикачі `autoGainControl` / noise-suppression; задокументуйте
- [ ] **Репетиція запасного варіанту**: посеред дзвінка перемкніть мікрофон Chrome на апаратну гарнітуру —
      чи застосовує це Zoho без перепідключення?
- [ ] **Spike B (~пів дня)**: той самий дзвінок через Voicemeeter Banana; задокументуйте
      робочу конфігурацію як перевірений запасний план B

**Go/no-go**: усе вище проходить → Phase 1. A провалюється → ухвалити відрепетирувану
конфігурацію Voicemeeter і переосмислити обсяг Phase 1 (рушій звужується до soundboard).
